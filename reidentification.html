System architecture.

The question

How can a distributed camera system recognise a previously seen person or vehicle while keeping the model, communication and persistent state working together?

What I built

On each edge node, YOLOv8n detects people and vehicles, ByteTrack tracks them within the camera view, and OSNet-AIN-x1.0 extracts a 512-dimensional embedding. The node sends the embedding and a thumbnail crop to a central FastAPI server for cross-camera matching. The server stores identities and sightings in PostgreSQL and reconstructs the identity gallery after a restart.

I wrote the database schema and queries for storing, updating and retrieving history. I also took responsibility for planning the server and data handling, discussing those decisions with my supervisor.

Improving the recognition results

Fine-tuning the vehicle backbone improved Rank-1 accuracy from 4.1% to 58.9% on the AIC21 CityFlow Track-2 query/gallery split. The training used real vehicle images and PAMTRI synthetic data.

Earlier in the project, I investigated weak recognition results, read other approaches and asked for advice. Adding detection before re-identification helped. That change is separate from the fine-tuning comparison above.

Data handling and limitations

The integration tests used three synthetic camera videos generated from dataset crops. These results do not establish performance on live camera deployments. The CPU-only pipeline achieved 1.1 FPS; the 102.2 FPS result requires the tested GPU configuration.

Raw video stays local, while embeddings and thumbnail crops are sent to the server. Embeddings and thumbnail crops can still contain identifying information. Matching, storage and network capacity still constrain the system as it grows.

What I learned

This project brought together my electrical-engineering, embedded-systems and AI background. I learned to think about recovery, data storage and the behaviour of the whole system alongside the recognition model.
